# Nx‑Rebuild‑New とは

本リポジトリは、新しい Web システム開発基盤である **Nxアーキテクチャ** を組み込んだ実装例です。

Nxアーキテクチャは、既存のエンタープライズ向け Web アーキテクチャ  
（Controller / Service / Repository / DTO / Validation 層など）を置き換えるのではなく、  
**既存構造の上に“追加モジュール”として組み込める抽象アーキテクチャ**です。

---

## Nxアーキテクチャの最大の特徴

### **クライアントとサーバが “まったく同じオブジェクト構造” を共有できること**

これにより：

- CRUD は宣言的になり  
- スキーマ変更は自動伝播し  
- 大規模システムでも構造的安定性を維持できます  

---

## 目的

- 個人開発者・AI支援開発・大規模チームが  
  **同じ構造で CRUD を書ける開発基盤** を確立すること  
- 分散システム構築を容易にし、複数クライアントの CRUD による  
  **データ不整合・システム破綻を防ぐこと**

Nx‑Rebuild‑New はそのために、  
CRUD の最小単位を **BaseDataObj** とする Nxアーキテクチャの実装例として開発されています。

---

# Nxアーキテクチャが提供するもの

### ✔ DataObj 中心の CRUD  
UI・API・DB が同じ構造を共有し、DTO やバリデーション層が不要になります。

### ✔ クライアントとサーバの完全同型化  
同じ DataObj を扱うため、CRUD の構造が安定し、スキーマ変更が自動伝播します。

### ✔ スキーマ変更への強い耐性  
Shared の構造がそのまま両側に反映されるため、仕様変更に極めて強い設計になります。

### ✔ CRUD 実装の単純化  
UI と API のコードがほぼ同一になり、新しいエンティティは **派生クラスを作るだけ** で完成します。

### ✔ エンティティ単位のモジュール化  
巨大なシステムでも構造が崩壊しない疎結合性を持ちます。

# 使い方（簡易版）

1. クライアント側でサーバのスキーマを読み込む  
   → 同じスキーマのインメモリ DB（WASM 推奨）を構築

2. `/Shared` フォルダの基底クラスをコピー  
   - BaseDataObj  
   - BaseDataObjMgr

3. 同期ラッパーを利用  
   - SyncBaseDataObj  
   - SyncBaseDataObjMgr

4. サーバ側では NxDataController を継承  
   → 派生クラスを作るだけで CRUD/API が完成

5. UI は DataObj を直接扱う  
   → WASM UI ならローカル DB と完全同型化される

# Nxアーキテクチャの概要（簡易版）

Nxアーキテクチャは  
**「BaseDataObj が CRUD の最小単位として動作する」**  
という原則に基づいています。

### 基本原則

- DB への直接操作は **BaseDataObj による CRUD のみ**  
- 複数エンティティにまたがる処理は  
  **BaseDataObj の集合に対するループ処理**  
- UI と「ユーザー入力エンティティ」が 1:1 の関係を持つ  
  （※ ユーザー入力エンティティ＝複数テーブルにまたがる入力の最小単位）

### 得られる効果

- エンティティ単位で機能を実装できる  
- 集計や複雑な処理は別モジュール化  
- 仕様変更に強い  
- クライアント／サーバが同一モデルを共有するため  
  CRUD の構造が安定する

---

# ローカル DB を持つ UI（WASM / デスクトップアプリ）の利点

Nxアーキテクチャの **多態性射影モデル（Divergence Oscillation Model）** は  
ローカル DB（SQLite / WASM FS / 各種ネイティブストレージ）前提のため、  
WASM UI やデスクトップアプリ（Electron / WPF / WinUI / Qt / Flutter Desktop 等）といった  
“ローカル DB を持つ任意の UI 環境”で以下が成立します：

- 動作環境を選ばず Nxアーキテクチャを開発基盤として利用可能  
- 同期あり／同期なしの CRUD が完全動作  
- BaseDataObj / BaseDataObjMgr によるエンティティ抽象化  
- 複数エンティティの集合を扱う UI の抽象化が成立する
- クライアント側でエンティティ管理（CRUD）を安全に自走可能  
- コピペ機能の実装が容易  
- UI 基底クラスが同期あり／なし両方を扱える  
  （エンティティタイプ別の入力画面も抽象化可能）  
- 既存システムへの侵襲ゼロで新しいエンティティ CRUD をボルトオン追加可能  
- ブラウザ UI の場合、既存 UI を「ページング専用」として段階的移行可能  
- デスクトップ環境では WASM より高速なローカル CRUD が可能  
- 大規模エンティティをローカルで安全に扱える

# 多態性射影モデル（Divergence Oscillation Model）

多態性射影モデルは、  
クライアントとサーバの状態が **多態化（divergence）** した際に、  
その差分を安全に扱うための抽象モデルです。

実態としては：

- 複数コンピュータが同型スキーマを共有し  
- エンティティを各自で自走するオブジェクトとし
- それらがデータのスナップショット（部分／全体）を保持・同期し  
- 整合性を維持しつつ  
- システム破綻を回避するための抽象構造  

各コンピュータは UI 層・作業層・保存層・正本層といった  
複数の射影（Projection）を形成し、  
差分・揺れ戻り・収束を管理することで  
分散環境でも **単一計算機としての一貫した振る舞い** を実現します。

この構造は：

- BaseDataObj  
- BaseDataObjMgr  
- Sync 系ラッパー  
- インターフェース準同型化構造  

によって支えられています。

---

# Nxアーキテクチャの結論：単一計算機モデル

Nxアーキテクチャは、  
UI 実装者・アプリケーションロジック実装者の視点において  
**分散環境を「単一の計算機」として扱える抽象化基盤**を提供します。

分散特有の破綻（同期ズレ・順序崩壊・再送・部分故障など）は  
BaseDataObj／SyncBaseDataObj によって吸収され、  
UI 実装者は分散の複雑性を扱う必要がありません。

ネットワーク断・DB 障害・サーバ停止などの物理層の挙動は  
CRUD 処理の外側に隔離され、  
アプリケーションロジックから切り離された領域として扱われます。

その結果：

- UI 実装者は「単一計算機」を扱うように開発でき  
- ネットワーク担当者は SyncBaseDataObj の限定領域のみを扱えばよくなる  

という構造的分離が成立します。
